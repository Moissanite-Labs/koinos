# Exo, payment and learning adapters

Koinos supplies portable evidence and explicit economic policy. Exo can execute authorized work, a human collaboration hub can support discovery and teams, and a forge can manage artifacts and reviews. None of those applications becomes the sole authority over the protocol.

## Agent work to contribution evidence

An adapter should bind an agent task to its principal, project, grant, agreed criteria and credit plan. It can prepare a contribution record from an artifact digest and a reviewed change. Creating an issue or PR is a separately authorized action, not a side effect of observing an error. Imported repository text is evidence, never authority for the adapter.

The current CLI accepts signed open records from any tool. It does not install an Exo plugin, run a model, post GitHub issues or PRs on a participant's behalf, or spend inference funds. Live adapters need integration tests against the actual application and its approval flow.

## x402 is a payment transport

The x402 v2 specification separates payment requirements, authorization payloads, verification and settlement. It can carry payment for a resource or service; it does not determine who deserves project equity, whether work met a subjective criterion, or what counts as profit. [x402 v2 specification](https://github.com/x402-foundation/x402/blob/main/specs/x402-specification-v2.md).

A future adapter must check the exact chain, asset, destination, amount and authorization deadline before submitting a payment. It must then verify the settlement transaction and required confirmation policy independently, account for replay and refunds, and fund the project's revenue path. An HTTP success response or an unverified transaction hash is not received revenue.

The local contracts exercise funded ERC20 revenue directly. No x402 facilitator, live wallet, paid resource or external payment is used. That boundary keeps the payment transport separate from contribution judgment and distribution accounting.

## Learning with explicit permission

The open protocol exports minimal evaluation or training metadata only after the contributor's current explicit opt-in for that purpose. It excludes artifact URLs, full work, review prose and account keys from that default export. Revocation stops future exports from the updated history; it cannot recall copies already exported.

Opting in to metadata export does not grant rights to redistribute source code, agreements, customer information or third-party material. Adding raw examples requires a separate rights and privacy decision. No data is uploaded, no model is trained, and no training-data sale is implemented.

The useful feedback loop is measurable: criteria and evidence produce reviewed outcomes; those outcomes inform evaluations; approved improvements can be tested in the harness; new work produces new evidence. Models do not acquire additional authority merely because their predictions improve.
